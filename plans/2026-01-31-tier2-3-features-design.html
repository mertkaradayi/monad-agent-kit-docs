Date: 2026-01-31 Features: Multiple wallet providers, LP position tracker, Name resolution

Feature 1: Multiple Wallet Providers ​

Problem ​

MonadAgentKit only supports private key wallets. Competitors (Coinbase, GOAT) support 3-12+ wallet providers.

Solution ​

Add EIP-1193 provider support to WalletConfig. Viem's custom() transport accepts any EIP-1193 provider, so MetaMask, WalletConnect, Privy, and injected providers all work.

Changes ​

packages/core/src/wallet.ts

typescript
import type { EIP1193Provider } from "viem"

export interface WalletConfig {
  privateKey?: `0x${string}`
  account?: Account
  provider?: EIP1193Provider  // NEW
  rpcUrl?: string
  chainId?: number
}

In createWallet():

  • If provider is set, use custom(provider) as transport
  • Derive account from provider via eth_requestAccounts
  • If privateKey is set, use current local account path
  • Exactly one of privateKey, account, or provider must be set

packages/core/src/agent.ts

  • Pass provider through to createWallet()
  • Add getPrivateKey() returns undefined when using provider (already handles this)

Feature 2: LP Position Tracker ​

Problem ​

addLiquidity creates orders but doesn't return order IDs. Users can't query their LP positions. removeLiquidity requires manual order ID input.

Solution ​

Add getLPPositions action to plugin-defi using Kuru SDK's PositionViewer/PositionProvider to query on-chain positions.

Parameters ​

typescript
interface GetLPPositionsParams {
  pool: string           // Kuru orderbook address
  address?: string       // Defaults to agent wallet
}

Result ​

typescript
interface LPPosition {
  orderId: number
  side: "bid" | "ask"
  price: string
  liquidity: string
}

interface GetLPPositionsResult {
  pool: string
  address: string
  positions: LPPosition[]
  totalBids: number
  totalAsks: number
}

Feature 3: Name Resolution ​

Problem ​

Users must type raw addresses. No name-to-address resolution exists.

Solution ​

Add an extensible NameResolver interface in core. Ship with no built-in provider (Monad has no name service yet). When a name service launches, we add a provider without changing the architecture.

Interface ​

typescript
// packages/core/src/names.ts
export interface NameResolver {
  resolveName(name: string): Promise<Address | null>
  supportsName(name: string): boolean
}

export async function resolveNameOrAddress(
  input: string,
  resolver?: NameResolver,
): Promise<Address | null> {
  const addr = normalizeAddress(input)
  if (addr) return addr
  if (resolver?.supportsName(input)) {
    return resolver.resolveName(input)
  }
  return null
}

Integration ​

typescript
// MonadAgentKit constructor
const agent = new MonadAgentKit({
  privateKey: "0x...",
  nameResolver: myResolver,  // optional
})

// Exposed on agent
agent.nameResolver  // NameResolver | undefined

Conflict Awareness ​

Shared files all 3 features touch: ​

  • CLAUDE.md — Each adds to Available Actions / Infrastructure section
  • README.md — Each adds a line to feature tables
  • docs/.vitepress/config.ts — Each adds a sidebar link
  • docs/ROADMAP.md — Each checks a box

Feature-specific files (no conflicts): ​

  • Wallet providers: packages/core/src/wallet.ts, packages/core/src/agent.ts
  • LP tracker: packages/plugin-defi/src/actions/getLPPositions.ts, MCP handlers/tools
  • Name resolution: packages/core/src/names.ts

Potential conflict: ​

  • Wallet providers and Name resolution both modify agent.ts — but in different sections (constructor config vs public property). Additive, easy merge.
  • LP tracker touches handlers.ts and handlers.test.ts — same as previous batches, additive appends.

Merge order recommendation: ​

  1. Name resolution (smallest, core-only)
  2. Wallet providers (core changes, no plugin impact)
  3. LP tracker (plugin + MCP, most files touched)
