Design: Batch 3 Features — Agent Memory, Event Monitoring, Limit Orders ​

Date: 2026-01-31 Features: Agent memory / tx log, Event monitoring, Limit orders

Feature 1: Agent Memory / Tx Log ​

Problem ​

No record of agent actions. Can't query what an agent did, track PnL, or build analytics. Every action result is fire-and-forget.

Solution ​

Hook into MonadAgentKit.execute() to log every action invocation. Pluggable TxLogStore interface with an in-memory default. Two query actions in plugin-tokens.

Types ​

typescript
// packages/core/src/txlog.ts

interface TxLogEntry {
  id: string              // UUID
  timestamp: number       // Unix ms
  action: string          // Action name
  params: unknown         // Input params (sanitized)
  success: boolean
  data?: unknown          // Result data on success
  error?: { code: string; message: string }
  transactionHash?: string
  gasUsed?: string        // From receipt if available
  chainId: number
  address: string         // Agent wallet address
}

interface TxLogQuery {
  action?: string         // Filter by action name
  success?: boolean       // Filter by outcome
  since?: number          // Unix ms, entries after this time
  limit?: number          // Max entries (default 50)
}

interface TxLogStore {
  append(entry: TxLogEntry): Promise<void>
  query(filter?: TxLogQuery): Promise<TxLogEntry[]>
  count(filter?: TxLogQuery): Promise<number>
  clear(): Promise<void>
}

In-Memory Implementation ​

InMemoryTxLogStore — array-backed, FIFO. Max 10,000 entries (configurable). query() filters and slices. Exported from core so users can extend or replace.

Integration with MonadAgentKit ​

typescript
// AgentConfig
interface AgentConfig extends WalletConfig {
  safety?: SafetyConfig
  nameResolver?: NameResolver
  txLog?: TxLogStore       // NEW — defaults to InMemoryTxLogStore
}

In execute(), after the action returns (success or failure), call this.txLog.append(entry). Logging is fire-and-forget — errors in append() are swallowed (logging should never break action execution).

Actions ​

getActionHistory (plugin-tokens)

  • Params: { action?: string, success?: boolean, since?: string, limit?: number }
  • Returns: { entries: TxLogEntry[], total: number }

getActionStats (plugin-tokens)

  • Params: { since?: string }
  • Returns: { totalActions: number, successCount: number, failureCount: number, uniqueActions: string[], totalTransactions: number }

Both read-only — no safety policy concerns.

Feature 2: Event Monitoring ​

Problem ​

No way to subscribe to on-chain events. Required for price alerts, copy trading, and autonomous agent behavior.

Solution ​

EventMonitor class in core using viem's watchEvent (polling-based). Three auto-registered actions for AI frameworks. Lazy initialization — no polling until first subscription.

Types ​

typescript
// packages/core/src/events.ts

interface EventFilter {
  address?: string        // Contract address to watch
  event?: string          // Event signature (e.g., "Transfer(address,address,uint256)")
  args?: Record<string, unknown>  // Indexed arg filters
  fromBlock?: "latest" | bigint
}

interface MonitoredEvent {
  id: string              // UUID
  subscriptionId: string
  blockNumber: bigint
  transactionHash: string
  address: string
  eventName: string
  args: Record<string, unknown>
  timestamp: number       // When we received it
}

interface Subscription {
  id: string
  filter: EventFilter
  createdAt: number
  eventCount: number
}

interface EventMonitorConfig {
  pollingInterval?: number  // ms, default 2000
  maxEventsPerSubscription?: number  // Ring buffer cap, default 1000
}

EventMonitor Class ​

typescript
class EventMonitor {
  constructor(publicClient: PublicClient, config?: EventMonitorConfig)

  subscribe(filter: EventFilter): string      // Returns subscription ID
  unsubscribe(id: string): boolean
  getEvents(subscriptionId: string, since?: number): MonitoredEvent[]
  getSubscriptions(): Subscription[]
  destroy(): void  // Stop all watchers, clean up
}

Each subscription starts a watchEvent poller. Events are stored in a per-subscription ring buffer (capped at maxEventsPerSubscription). destroy() calls unwatch() on all active pollers.

Integration with MonadAgentKit ​

The EventMonitor is created lazily on first subscription action call. Stored as a private field on MonadAgentKit. Three actions auto-registered in the constructor (like readContract/writeContract).

typescript
// AgentConfig
interface AgentConfig extends WalletConfig {
  safety?: SafetyConfig
  nameResolver?: NameResolver
  txLog?: TxLogStore
  events?: EventMonitorConfig  // NEW — optional polling config
}

Actions (core, auto-registered) ​

subscribeEvents

  • Params: { address?: string, event?: string, args?: object }
  • Returns: { subscriptionId: string, filter: EventFilter }

getEventLog

  • Params: { subscriptionId: string, since?: string, limit?: number }
  • Returns: { events: MonitoredEvent[], total: number }

unsubscribeEvents

  • Params: { subscriptionId: string }
  • Returns: { success: boolean }

Feature 3: Limit Orders ​

Problem ​

No way to place limit orders. Users can swap at market price but can't set a target price and wait.

Solution ​

Wrap Kuru's LP system as limit orders. A limit order is a single-sided LP position at a specific price. Uses PositionViewer + PositionProvider (existing SDK). Three actions in plugin-defi.

How It Works ​

Kuru is a CLOB — liquidity provision creates resting orders on the book. A "buy limit at $X" is an LP bid at price X. A "sell limit at $X" is an LP ask at price X.

Implementation:

  1. Fetch market params via ParamFetcher.getMarketParams()
  2. Use PositionViewer.getBidAskBatchLPDetails() with only one side (bid or ask)
  3. Place via PositionProvider.provisionLiquidity()
  4. Parse tx receipt to extract order IDs
  5. Cancellation uses PositionWithdrawer.withdrawLiquidity()

Conflict Awareness ​

Shared files all 3 features touch: ​

  • CLAUDE.md — Each adds to Available Actions section
  • README.md — Each adds to action tables
  • docs/.vitepress/config.ts — Each adds sidebar links
  • docs/ROADMAP.md — Each checks a box
  • examples/mcp-claude-desktop/src/handlers.ts — Additive handler appends
  • examples/mcp-claude-desktop/test/handlers.test.ts — Additive test appends

Feature-specific files (no conflicts): ​

  • Tx log: packages/core/src/txlog.ts, packages/plugin-tokens/src/actions/getAction*.ts
  • Event monitoring: packages/core/src/events.ts, packages/core/src/actions/*Events.ts
  • Limit orders: packages/plugin-defi/src/actions/*LimitOrder*.ts

Potential conflict: ​

  • Tx log and Event monitoring both modify packages/core/src/agent.ts — tx log hooks into execute(), events adds lazy EventMonitor + auto-registers actions. Different sections, additive.

Merge order: ​

  1. Limit orders (smallest — plugin-defi only, no core changes)
  2. Agent memory / tx log (core + plugin-tokens, hooks into execute())
  3. Event monitoring (core, most files, rebases on tx log's agent.ts changes)
