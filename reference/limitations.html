Known Limitations ​

This page documents known limitations and constraints when using the Monad Agent Kit.

Liquidity Provisioning ​

Pool minSize Constraint ​

Kuru DEX pools have a minSize parameter that sets the minimum size for each individual order/position. When adding liquidity across a price range:

  • The SDK creates multiple bid/ask positions across your specified range
  • Each position must meet the pool's minSize requirement
  • Total liquidity ÷ number of positions must exceed minSize

Symptoms:

  • MIN_SIZE_ERROR when calling addLiquidity
  • "Position size below minimum" error

Solutions:

  1. Check pool's minSize via getPoolInfo first
  2. Use a tighter price range to create fewer positions
  3. Increase your liquidity amount
  4. Find pools with lower minSize requirements

Example: The MON/USDC pool has minSize: 2×10^12. With a price range creating 50 positions, you'd need each position to hold at least 200 normalized units.

typescript
// Always check pool constraints before adding liquidity
const poolInfo = await agent.execute("getPoolInfo", { pool: poolAddress })
console.log("Pool minSize:", poolInfo.data.minSize)
console.log("Pool sizePrecision:", poolInfo.data.sizePrecision)
console.log("Pool tickSize:", poolInfo.data.tickSize)

SDK Calculation Constraints ​

When using baseLiquidity input, the SDK performs reciprocal sum calculations that can fail with very small amounts or wide price ranges:

  • Error: "reciprocalSumScaled is zero"
  • Cause: Integer division underflow when calculating position sizes
  • Solution: Use quoteLiquidity instead, or increase amount/tighten range

Native Token (MON) Pool Limitations ​

Pools where native MON (address 0x0) is the quote token may have issues with liquidity provisioning:

  • Issue: The Kuru SDK's liquidity provisioning may not properly send native MON value with the transaction
  • Error: "execution reverted" or contract error during addLiquidity
  • Workaround: Use pools where both tokens are ERC20s (e.g., WMON/USDC instead of MON/USDC)

aPriori Staking ​

Unstake Waiting Period ​

The aPriori liquid staking protocol requires a waiting period between requesting an unstake and claiming your MON:

  1. Request Unstake → Returns a requestId
  2. Waiting Period → Protocol-defined delay (typically hours to days)
  3. Claim Unstake → Use the requestId to claim

Symptoms:

  • claimUnstake fails with "not claimable" or "NotFinalized"

Solution:

  • Store the requestId from the requestUnstake response
  • Wait for the protocol's waiting period to pass
  • Check if claimable before attempting to claim
typescript
// Request unstake
const request = await agent.execute("requestUnstake", { shares: "1.0" })
const requestId = request.data.requestId // Store this!

// Later, try to claim (will fail if waiting period not passed)
const claim = await agent.execute("claimUnstake", { requestId: parseInt(requestId) })

Network-Specific Limitations ​

aPriori Mainnet Only ​

The aPriori staking protocol is only available on Monad mainnet (chainId: 143). Staking actions will return an error on testnet.

Affected actions:

  • stake
  • requestUnstake
  • claimUnstake
  • getStakeInfo

Kuru API Availability ​

Some Kuru operations depend on their API service (api.kuru.io). If the API is temporarily unavailable:

  • getQuote with Kuru source may fail
  • Pool discovery via API may fail
  • Swap routing may be limited

Workaround: Use getPoolInfo with a known pool address (direct contract call, more reliable than API).
